**날짜:** 2026-08-11

### 1. 문제 분석

- **요구사항:** `ExcelDataSource` 인터페이스와 로컬 파일 구현체를 추가하고, 주보·출석·대표기도가 파일 경로 대신 데이터소스를 통해 Workbook과 메타데이터를 사용하게 한다.
- **현재 코드 상태:** #21에서 `ExcelReaderService`가 Workbook 입력을 지원하지만 `BulletinController`와 `RepresentativePrayerService`는 여전히 설정 파일에서 엑셀 경로를 직접 조회한다.
- **후속 의존성:** #23의 Google Drive 구현체가 같은 인터페이스 뒤에 추가될 예정이다.
- **핵심 제약:** 기존 로컬 경로 설정 UI와 파싱 결과를 유지하고, 데이터소스가 연 Workbook은 호출자가 반드시 닫아야 한다.

### 2. 검토한 접근 방법

| 방법 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| 각 호출부에서 InputStream을 열어 리더에 전달 | 변경 파일이 적음 | 호출부가 계속 경로와 저장 위치를 알아야 함 | ✗ |
| 데이터소스가 파싱 결과까지 반환 | 호출부가 단순함 | 주보·출석·대표기도 파싱 책임이 데이터소스에 중복됨 | ✗ |
| 데이터소스는 Workbook과 메타데이터만 제공하고 기존 리더가 파싱 | 책임 분리가 명확하고 #21 Workbook API를 그대로 재사용 | 호출자가 Workbook 종료 책임을 가짐 | ✓ |

### 3. 결정 및 근거

채택: **Workbook 공급 전용 데이터소스**

- `ExcelDataSource`는 `getActiveWorkbook()`과 `getMetadata()`만 제공한다.
- `LocalFileExcelSource`는 기존 환경변수 기본값과 `TextConfigService`의 화면 설정값을 한 곳에서 해석한다.
- 로컬 버전은 파일 크기와 수정 시각으로 구성하고, 해시는 JDK의 SHA-256으로 계산한다.
- 주보·출석·대표기도 호출부는 try-with-resources로 Workbook을 닫고 기존 `ExcelReaderService`의 Workbook 오버로드를 호출한다.
- 설정된 경로가 없을 때의 기존 화면 동작은 메타데이터의 빈 경로로 판별해 유지한다.
