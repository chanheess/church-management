# 에이전트 결정 로그

## 이슈 #21 — [데이터] ExcelReaderService를 Workbook/InputStream 입력 기반으로 리팩터

**날짜:** 2026-08-08
**브랜치:** feature/21
**작업자:** Codex (GPT-5)

---

### 1. 문제 분석

- **요구사항:** `ExcelReaderService`가 파일 경로뿐 아니라 `InputStream` 또는 Apache POI `Workbook`을 입력으로 받아 기존 파싱 로직을 재사용하게 한다.
- **현재 코드 상태:** 명단, 주보, 출석 공개 메서드가 각각 `String filePath`를 받고 내부에서 `FileInputStream`과 `XSSFWorkbook`을 직접 생성한다. 이 구조에서는 Google Drive 다운로드 바이트나 업로드 스트림을 경로로 임시 저장하지 않고 사용할 수 없다.
- **후속 의존성:** #22의 `ExcelDataSource`와 #23의 `GoogleDriveExcelSource`가 이 입력 경계를 사용한다.
- **핵심 제약:** 기존 경로 기반 호출부와 화면 결과는 그대로 유지해야 하고, 스트림·워크북의 소유권과 종료 책임이 모호해지면 안 된다.

### 2. 검토한 방법

| 방법 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| 기존 경로 메서드와 새 스트림 메서드에 파싱 로직 복제 | 구현이 단순해 보임 | 로직이 즉시 중복되고 이후 수정 시 결과 불일치 위험 | ✗ |
| `InputStream`만 공개하고 내부에서 `WorkbookFactory` 사용 | #23에 필요한 바이트 입력 지원, 변경량 작음 | 테스트나 #22가 이미 열린 Workbook을 재사용하기 어려움 | △ |
| 경로 → InputStream → Workbook → 순수 파싱 메서드의 계층형 어댑터 | 기존 API 호환, 모든 입력원 지원, 파싱 로직 단일화 | 공개 오버로드 수가 늘어남 | ✓ |

### 3. 결정 및 근거

채택: **계층형 어댑터**

- 기존 `String filePath` 메서드는 유지하고 `Files.newInputStream`으로 얇게 위임한다.
- `InputStream` 오버로드는 `WorkbookFactory.create`로 형식을 판별하고 생성한 Workbook을 닫는다. 전달받은 InputStream은 호출자가 닫는다.
- `Workbook` 오버로드가 실제 시트 선택과 파싱을 수행한다. 전달받은 Workbook은 호출자가 소유하므로 닫지 않는다.
- `XSSFWorkbook` 직접 생성 의존을 제거해 POI가 지원하는 Workbook 형식을 같은 경계에서 처리한다.
- 입력 null은 즉시 실패하도록 명확히 검증한다.

이 구조는 #21 범위 안에서 현재 호출부를 깨지 않으면서 #22·#23이 파일 경로 없이 데이터를 공급할 수 있는 최소 기반이다.
