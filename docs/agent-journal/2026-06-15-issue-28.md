# 에이전트 결정 로그

## 이슈 #28 — [보안] 개인정보 필드 암호화 (이름·생년월일·전화번호, AES-256-GCM)

**날짜:** 2026-06-15
**브랜치:** feature/28
**작업자:** Claude (claude-opus-4-x)

---

### 1. 문제 분석

- **요구사항(#3):** `Member`의 PII(이름·생년월일·전화번호)를 저장 시 암호화, 조회 시 자동 복호화. ISMS-P 2.7(암호화 적용) 대응.
- **현재 상태:** `Member`(data.member)는 평문 저장. 비밀번호는 feature/03에서 BCrypt(별개). DB는 H2(local)·PostgreSQL(server) 예정.
- **제약:**
  - 검증된 알고리즘만(AES-256-GCM).
  - 키는 소스·.env(커밋본) 금지 → 주입. 시크릿 스캔(#26)이 키 커밋 차단.
  - `MemberRepository`는 연도·셀로만 조회 → 이름/전화/생년월일 동등검색 없음 → **블라인드 인덱스 현재 불필요**.
  - 로컬 데스크톱 실행과 기존 테스트(@SpringBootTest)가 깨지면 안 됨.

---

### 2. 검토한 접근 방법

| 주제 | 선택지 | 결정 |
|------|--------|------|
| 암호화 위치 | DB 전체 암호화(TDE) vs **필드 단위(JPA Converter)** | 필드 단위 — 이식성·세밀함 |
| 알고리즘 | AES-CBC vs **AES-256-GCM** | GCM(인증 암호, 변조 탐지) |
| 검색 | 결정적 암호화 vs 블라인드 인덱스 vs **없음** | 현재 검색 안 함 → 없음(후속에 HMAC) |
| 컨버터↔키 주입 | Hibernate DI vs **정적 홀더** | 정적 홀더(테스트·슬라이스에서 안정) |
| 키 부재 시 | **fail-fast** vs 임시키+경고 | 초기엔 임시키+경고, 이후 fail-fast로 변경 |

---

### 3. 결정 및 근거

- `security.crypto` 패키지:
  - `AesGcmCipher` — 랜덤 IV(12B)+GCM(128b 태그), `IV‖ct` base64. 키 32B 강제.
  - `PiiCipherHolder` — 컨버터(Hibernate가 생성, DI 없음)가 쓰는 정적 브리지.
  - `PiiCryptoConfig` — `app.security.pii-key`(base64 32B) 읽어 cipher 생성·홀더 주입. 키 없으면 **기동 중단(fail-fast)**.
  - `EncryptedStringConverter`(전화), `EncryptedLocalDateConverter`(생년월일).
- `Member.phone/birthDate`에 `@Convert`(이름은 평문 — §7 참고).
- 테스트: 암호 유닛 + `@DataJpaTest`에서 홀더 초기화 후 **DB 원본 컬럼이 평문 아님**을 네이티브 쿼리로 검증.

근거: 필드 단위 GCM은 이식성·무결성을 함께 주고, 정적 홀더는 Hibernate가 생성하는 컨버터에 키를 안정적으로 공급한다(슬라이스 테스트에서도 동작).

### 7. 설계 변경 (이름 암호화 제외)

초기엔 이름·전화·생년월일 셋 다 암호화했으나, **이름은 평문으로 되돌림**.

**근거:**
- 이름은 **주보에 공개 인쇄**되는 정보 → 저장 암호화의 비밀유지 이득이 작음.
- **법상 저장 암호화 의무 대상 아님**(비밀번호·고유식별정보가 의무). 이름은 접근통제로 보호.
- **가장 자주 조회·정렬**되는 필드 → 암호화하면 DB 검색/정렬/LIKE 불가. 평문이 운영상 유리.
- 복호화 비용은 무시 가능(AES-GCM μs 단위)했으나, 비용이 아니라 **검색 기능 제약**이 핵심 이유.

**결과:** `Member.name` `@Convert` 제거(평문). `phone`·`birthDate`는 암호화 유지. 테스트도 "이름=평문, 전화·생년월일=암호문"으로 조정.

### 8. 설계 변경 (키 부재 시 fail-fast)

**날짜:** 2026-07-21

초기엔 키 미설정 시 임시 랜덤키+경고로 기동했으나, **키 미설정 시 기동 중단(fail-fast)으로 변경**.

**근거:**
- 이슈 #28 본문이 "미설정 시 fail-fast(운영), 테스트는 테스트 키"를 명시적으로 요구 — 임시키 폴백은 이 요구 미충족.
- 임시키는 재시작마다 바뀌어, 키 미설정 상태로 PII가 저장된 뒤 재시작하면 기존 암호문을 영구 복호화 불가(개인정보 영구 손실). 경고 로그만으로는 운영자가 놓치기 쉬움.
- 이 앱은 프로필이 없는 단일 데스크톱 앱이라 unconditional fail-fast가 이슈 의도와 정확히 일치.

**결과:**
- `PiiCryptoConfig` — 키 blank/null이면 `IllegalStateException`으로 기동 중단(임시키·경고 로그 제거).
- `ChurchManagementApplicationTests` — `@SpringBootTest`에 테스트 키 주입(fail-fast로 인한 컨텍스트 로딩 실패 방지).
- `PiiCryptoConfigTest` 신규 — blank/null→예외, 정상키→로드 검증.
- `PiiCipherHolder` — 병렬 테스트 시 전역 상태 교차오염 가정을 Javadoc에 명시(현재 순차 실행이라 미발현).
- 로컬 실행은 `.env`의 `APP_PII_KEY`로 정상 기동. 커밋 `3c04639`.
